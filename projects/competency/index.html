01 — Problem

Assessing competency across 400+ roles, by hand

Technical competency reviews were run out of spreadsheets: every role had its own set of expected behaviors, managers scored them by hand, and HR stitched the results back together for reporting. At the scale of 404 job roles and 3,000+ key behaviors, that is slow, inconsistent between managers, and nearly impossible to audit.

The brief was a real application HR and managers log into — one that holds the whole competency framework, guides a consistent assessment, and produces defensible reports without anyone touching a spreadsheet.

02 — Approach

A framework the app enforces, not a form it displays

The competency framework — roles, competencies, and the key behaviors under each — is modelled as data, imported once and enforced everywhere. A manager assessing an employee only ever sees the behaviors that belong to that role, and the scoring adapts to the answers:

  • Role-scoped behaviors404 rolesEach assessment is generated from the target role — no irrelevant criteria, no manual setup.
  • Adaptive scoringprobe ±1 levelResults automatically probe one proficiency level up or down, so the assessment homes in on the real level instead of asking everything.
  • HR dashboardperiod filtersResults roll up with period filters and a one-click Excel export — a summary plus a per-behavior audit trail.
Design decision — trust boundary

The browser only ever submits checkboxes. Every score is derived server-side from the framework — results are never trusted from the client — so a tampered request can't inflate a rating. Behind domain-restricted auth, covered by 48 unit tests.

03 — Architecture

From Excel source to audited report

A Python ETL step imports the framework from the client's Excel sources into Postgres. The assessment app reads role-scoped behaviors from there; when a manager submits, the scoring runs on the server and writes a result HR can filter and export.
